# Manager agent API

A small, token-authenticated HTTP endpoint that lets a manager's AI agent perform
a whitelisted set of manager actions against the live site. It is the "simplest
way to plug in an agent": a bearer token + JSON, wrappable as an MCP server or
driven directly by the bundled skill.

> Read this before changing `src/routes/api/manager/agent.ts`,
> `src/lib/manager-agent.ts`, or the agent schemas in `src/lib/validation.ts`.
> You do not need it for anything else.

- **Endpoint:** `src/routes/api/manager/agent.ts`
  - `GET  /api/manager/agent` → the self-describing **manifest** (the runtime
    source of truth for the current action set).
  - `POST /api/manager/agent` with `{ "action", "params" }` → dispatch.
- **Auth:** `Authorization: Bearer <token>`. Tokens are **manager-issued and
  revocable** — a manager mints them at `/manager/api-tokens` (route
  `_authenticated/manager.api-tokens.tsx`). Only a SHA-256 hash is stored
  (`manager_api_tokens` table); the raw token is shown once at creation. On each
  request the endpoint looks the token up by hash, confirms it isn't revoked, and
  re-checks the owner still holds the `manager` role. The endpoint runs actions
  with the service-role client, so a token grants manager-level access to the
  exposed actions — treat it as a secret.
  - **A minted token is the only credential this endpoint accepts.** There is no
    environment-variable fallback and there should not be one: an env key cannot
    be revoked without a redeploy, is stored in plaintext, never expires, is not
    re-checked against the owner's role, and belongs to nobody — so anything it
    wrote (a filed waiver, a published article) named no auth user. If every
    token is lost, a manager signs in and mints another at `/manager/api-tokens`;
    that needs only a manager login, which is why no separate break-glass
    mechanism is warranted. Please do not add one back.
  - Token management server functions: `src/lib/manager-api-tokens.functions.ts`
    (`listApiTokens` / `createApiToken` / `revokeApiToken`); token crypto +
    the paste-able agent prompt: `src/lib/manager-api-tokens.ts`.
  - The `/manager/api-tokens` screen also renders a copy-paste **agent prompt**
    (`buildAgentPrompt`) for Claude Code / opencode / Cursor and points at the
    `uts-manager-agent` skill.

## MCP server

The same actions are also served as an MCP server at `/mcp`, for assistants
that speak MCP (Claude Code, Claude, Cursor). It is a second front door onto
the same code, not a second implementation.

- **Code:** `src/lib/mcp/` (`defineMcp` in `index.ts`, one tool per file under
  `tools/`). The routes (`src/routes/mcp.ts`, the
  `/.well-known/oauth-protected-resource` metadata) are generated by
  `mcpPlugin()` in `vite.config.ts`; never hand-edit them.
- **Shared logic:** both doors call `dispatch` and `errorResponse` in
  `src/lib/manager-agent-actions.ts`, so an action behaves, refuses and reports
  errors identically over HTTP and MCP. Change actions there, not in either
  front door.
- **The MCP door accepts a request as large as the largest action input**: a
  paper waiver's scans, sent as base64. The SDK's own default is 1 MiB, and
  anything over it gets a 413 before the tool runs, which a waiver scan over
  about 750 KB used to hit. The figure is derived from the actions' file limits
  in `src/lib/mcp/limits.ts`, so raising one of those raises it too.
- **Auth is OAuth, not a minted token.** The assistant registers itself with
  the club's Supabase Auth OAuth 2.1 server, sends the manager to
  `/.lovable/oauth/consent` (`src/routes/[.]lovable.oauth.consent.tsx`) to sign
  in and approve, and then calls `/mcp` with the resulting access token. The SDK
  verifies the token (issuer, audience, and an OAuth `client_id` claim, so a
  copied browser session token is refused). Each tool call then checks
  `has_role(manager)` **as the signed-in person** before anything reaches the
  service-role code, and the acting user is always the token's subject. The
  "minted token is the only credential `/api/manager/agent` accepts" rule above
  still holds: that endpoint is unchanged.
- **What approving hands over is a full sign-in, not just the tools.** The
  access token is an ordinary Supabase session token for the manager, so it
  also works against the database directly, with everything that manager's RLS
  allows. A minted token reaches only the whitelisted actions. The consent page
  and `/manager/api-tokens` both say so, and two guards on the consent page
  follow from it:
  - It names **where the approval is sent** (the client's registered
    `redirect_uri`: a host, "this computer" for a loopback address, or an app's
    URL scheme; `src/lib/oauth-consent.ts`). Assistants register themselves, so
    the client _name_ can be anything; the redirect address is the one thing a
    lookalike cannot borrow.
  - It **never offers Approve to a non-manager**, and never passes one back
    to an assistant they approved earlier (the role check runs before the
    "already approved" shortcut). They get "Use a different login" and, where
    there is still a request to deny, "Cancel the request". This is a guard in
    the page, **not a server rule**: the OAuth server would still approve a
    member who called it directly. What holds regardless is the tools
    refusing them. Closing that fully needs a Supabase Auth hook and so a
    database change; it has not been made.
  - It **won't approve a destination it can't name** (an unparseable redirect
    address, or a `javascript:` / `data:` / `file:` one): Approve is disabled.
- **Disconnecting:** `/manager/api-tokens` lists the manager's own connected
  assistants (`supabase.auth.oauth.listGrants`) with a Remove button
  (`revokeGrant`). That deletes the assistant's sessions and refresh tokens, so
  it cannot sign back in without asking again; an access token it already holds
  stays valid until it expires (the project's JWT lifetime, normally an hour),
  because both the SDK and PostgREST verify it locally. Losing the manager role
  cuts the tools off at once regardless, since every call re-checks it. It
  does **not** remove the assistant's grant, and the list lives on a
  manager-only page, so a demoted manager's assistant keeps a member-level
  sign-in until somebody revokes it (a known gap, not handled yet).
- **Three tools:** `club_manifest` (returns `AGENT_MANIFEST`), `club_read`
  (only `list_*` / `get_*` actions, marked read-only so an assistant may run it
  without asking) and `club_change` (everything else, marked destructive). The
  split is `src/lib/mcp/actions.ts`; a new action lands on the change side
  unless its name says it reads.
- **After changing a tool or adding an action,** regenerate the MCP manifest
  (`bunx lovable-mcp-extract-manifest`, which rewrites
  `.lovable/mcp/manifest.json`), commit it, and republish; the published site
  keeps serving the old tool list until then. Lovable's commit pipeline does
  this for its own commits but not for anyone else's, so
  `src/lib/mcp/actions.test.ts` fails when the committed manifest disagrees
  with the action split or with a tool's title, description or annotations.

## Actions

An "invoice" is a `memberships` row — its price/reference/status _are_ the invoice.

- `list_users` — members and their lifecycle status, roles, and invoices, plus
  the cheap headline fields the person page leads with: `phone`,
  `email_confirmed_at` (null means not verified) and `code_of_conduct` (the same
  object `get_user` reports). The acceptances are read once, for the people on
  the returned page, not once per person.
- `get_user` — one person, as `/manager/users/<id>` shows them. It is that
  page's own read: `loadClubUser` in `src/lib/club-user.functions.ts`, which
  `getClubUser` also calls, projected by `projectAgentUser` in
  `src/lib/manager-agent.ts`. It has no query of its own, and must never grow
  one (see "Keep these in sync"). Profile, household, memberships, attendance,
  code of conduct and every waiver with its approval state. Two things differ
  from the page, both on purpose:
  - **What it leaves out is listed, not implied.** `GET_USER_LEFT_OUT` names
    each field of the read the API does not report, with its reason; today that
    is a waiver's `signer_ip` and `signer_meta` (forensic evidence no agent
    workflow needs). The one thing the page reads out of `signer_meta`, whether
    the waiver is a scanned paper form, is reported as `is_paper`. A test fails
    if the read gains a field that is neither reported nor listed.
  - **It refuses a half-read.** The page shows a failed address lookup as no
    address, a failed code-of-conduct read as "not signed yet", and a failed
    guardian, class or approver lookup as an unknown name, so a manager can
    still approve somebody. The read lists each of those in `degraded` (which
    the page itself never receives), and `get_user` turns a non-empty list into
    `500 db_error`: an agent cannot see the server log, and would act on the
    guess. An id with no person record (a lead) is `404 not_found`.

  Its `memberships` are the page's shape, not `list_users`' `invoices`: they
  carry `kind`, `plan_window` and `checkin_count` (the delete blocker), and leave
  the money detail (`payment_method`, `notes`, `plan_code`, `is_student`) to
  `invoices`. A person's item invoices, shown on the same page, are
  `list_item_invoices {"user_id"}`.

- `list_invoices` — invoices with member name/email (to find an id to edit).
  Every invoice here and in `list_users` carries `insurance_reminder`: null
  unless it is yearly insurance, otherwise whether its "ending soon" reminder is
  owed and which reminder was last emailed. The same projection as the
  memberships screen (`docs/memberships.md`, "When yearly insurance ends").

> [!IMPORTANT]
> **An address on a person's row is not always that person's mailbox.** Somebody
> on somebody else's account — a child, typically — has no address of their own
> (`docs/waivers.md` has the reserved-address rule), so the `email` on their
> `list_users` row and the `member_email` on their `list_invoices` row are the
> **guardian's**. Both listings say whose it is in a field beside it,
> `email_belongs_to` and `member_email_belongs_to`, null when the address really
> is the person's own. A caller reporting an address without that caption tells
> a manager they can write to a nine-year-old, which is the failure the split
> exists to prevent — so print the two together or not at all. Neither field is
> editable: `member_email_belongs_to` is a read-only decoration like
> `member_name`, and `edit_invoice` refuses it by name.

> [!NOTE]
> **The family, on a `list_users` row.** `guardian_user_id` is the account holder
> this person is on, or null for almost everybody: `email_belongs_to` **names**
> that person for a caption, this **identifies** them, so a caller can fetch or
> act on the guardian rather than only mention them. `dependants` is the people
> on this person's account, each `{ user_id, name }` — always present, empty for
> almost everybody, and empty for a dependant too, because a household is one
> level deep and a dependant can never have any.
>
> **Read `dependants` rather than rebuilding it** from `guardian_user_id` across
> the listing. A `status` filter can drop the children out of the response while
> leaving the parent in it, and a household reconstructed from what came back
> would then report that parent as having none.
>
> This is also how a caller learns that `create_membership` on a nine-year-old is
> a thing the club expects, and who to chase for the invoice it raises: billing
> is one invoice per child, and every one of them is delivered to the guardian.

> [!IMPORTANT]
> **`lifecycle_status` and `roles` reach through the household, and that moves
> what `status` filters.** A person counts as a `member`, and carries the
> `member` role, while anybody on their account holds an active paid membership.
> So a parent who does not train reads as `member` rather than `lead` or
> `lapsed`, which is what members-only access has said about them since the
> household shipped; it was the label that disagreed.
>
> Because `status` filters on that field, `list_users {"status":"lead"}` no
> longer returns such a parent and `{"status":"member"}` now does. Anything you
> cached that was filtered by status needs re-reading (manifest `"17"`).
>
> Only that one branch reaches. `lapsed` is still the person's own, so a parent
> whose own plan ended is still somebody to chase. And `member` remains a
> **label**: no policy reads the role, and it does not mean they are covered to
> train. Check-in coverage is strictly personal, so a parent at the door
> correctly shows no cover.

- `create_membership` — raise a membership for a person, the agent's equivalent
  of the manager screen's "Add a membership" and of a member choosing a plan
  themselves. Dispatches to `createMembershipForUser` in
  `src/lib/membership.functions.ts`, the same function the screen posts to, so
  an agent-raised membership and a manager's own are identical. It is
  **authorised immediately**, whatever the plan costs: the person can be checked
  in from that moment, with the invoice outstanding. Paying is a separate event
  (`mark_invoice_paid`, or bank reconciliation), and `reference` in the result is
  non-null exactly when money is owed. Two things it can do
  that a member's own purchase cannot, both for the same case — a manager
  writing down an enrolment that already happened: it accepts a plan that is no
  longer on sale (backfilling a past training period), and its
  `include_insurance` answer is final rather than enforced. `send_email: false`
  records the invoice without invoicing anybody for it. Re-raising the same
  person + plan reuses their existing unpaid invoice rather than creating a
  second one, so a retry is safe; the free trial is still once per person ever
  (`409 trial_already_used`), and an unknown plan code is `404 plan_not_found`.
  `starts_on` (default today) says when the membership itself runs from, and is
  the other half of a backfill — `send_email: false` keeps the invoice quiet,
  `starts_on` puts the cover where it actually ran. Only a plan whose start is a
  real choice takes one (`planStartIsChoosable`, so the yearly insurance);
  anything else is `422 start_date_not_choosable` rather than a date silently
  dropped. A bundled insurance invoice always runs from today: it is a second
  plan being sold now, not part of the backfill.
- `mark_invoice_paid` — record a payment against an invoice, for money that never
  touches the club account (cash at the door). Dispatches to
  `recordMembershipPayment`, the same writer bank reconciliation uses, so a
  payment recorded by an agent and one matched off a statement are the same
  event. It is the **only** manual writer of `paid_at`, emails the member a
  receipt, and is what makes an invoice permanently undeletable. Idempotent: a
  second call records nothing, moves no date and sends no second receipt, and
  comes back `recorded: false` — reconciliation legitimately sees the same
  invoice twice. Refused with `422 nothing_to_pay` on a free membership. Written
  to the server audit log with the actor, even when nothing was recorded.
  Optional `paid_on` (`YYYY-MM-DD`, default today, also when sent as `""` or
  null; never in the future or more than two years back, since nothing can
  correct it afterwards; may precede the invoice for a backfill) and `paid_reference` (a receipt number, up
  to 200 characters) record when the money arrived and what it was known by;
  `mark_item_invoice_paid` takes the same two (`"20"`). `paid_reference` is not
  `payment_reference`, which marking paid never changes. A past day is stored
  as noon Sydney time, so it reads back as the same date anywhere in
  Australia. Both list actions return `paid_reference`.
- `edit_invoice` — correct an invoice's detail fields. Cannot set `status` to
  `active`: reopening a closed membership recomputes its dates and credits, which
  is `setMembershipStatus`'s job, not a raw field edit's. Returns `changed` + `previous`
  alongside the updated invoice, and writes an audit line to the server log
  (`[agent.edit_invoice] audit`) naming the actor and each field's old → new.
  **On a paid invoice** (`paid_at` set) the money fields — `price_cents`,
  `payment_reference`, `payment_method` (`RECONCILED_GUARDED_FIELDS`) — are
  refused with `409 reconciled_invoice` unless `confirm_paid_edit` is passed:
  a reconciled invoice's amount is a record of money that moved, and the
  status it belongs to is already protected. `notes` and `status` stay freely
  editable (a note claims nothing about money; expiring a membership that ran
  its course is ordinary), and so is `starts_on`: it corrects the day a
  membership began, writing `starts_at` **and** `ends_at` through
  `rescheduleMembershipStart` so the window keeps the length it was sold at and
  moves as one. It is unguarded on purpose — dates say when somebody is covered,
  not what they paid, and the correction is wanted most often precisely because
  the money already landed. Same `422 start_date_not_choosable` on a plan with no
  start date to set, refused before anything is written. There is **no audit table** — if the log is not
  enough for the club's bookkeeping, that is a schema change and a product
  decision, not something to add quietly. Setting `status` to `cancelled` or
  `expired` also reconciles the person's `member` role (`syncMemberRole`), so
  `list_users` stops calling somebody a member once their last paid membership
  closes. Members-only **access** was never gated on that role — it is gated
  live by the `has_active_paid_membership` SQL helper — so this corrects a label
  that used to be granted and never taken back, and changes nobody's access.
  Since #107 that reconciliation reaches through the household: a person's label
  counts the memberships of everybody on their account, and closing a **child's**
  membership re-syncs the **parent** as well as the child. So a parent who does
  not train reads as a `member` while their child's plan is live, which is what
  the members-only gate has said about them since #103. It is still only a label:
  no policy anywhere reads the `member` role.
- **Item invoices** (`"18"`): `list_items`, `save_item`, `delete_item` keep the
  price list; `list_item_invoices`, `create_item_invoice`,
  `mark_item_invoice_paid`, `cancel_item_invoice`, `delete_item_invoice` raise
  and settle invoices from it. Each dispatches to the same shared function in
  `src/lib/item-invoices.functions.ts` that the manager screens call. An item
  invoice is **not** a membership row, so the "invoice" actions above never
  see one. `create_item_invoice` takes a `client_submission_id` so a retry
  cannot raise and email twice, and refuses a price on a line (the price list
  is the only source of price). Refusals: `404 not_found`,
  `409 item_invoice_settled` (cancel or delete of a paid invoice),
  `422 item_not_listed`. Product rules: `docs/item-invoices.md`.
- `get_club_settings` (`"21"`) — the club-wide settings `/manager/settings`
  edits, read through `loadClubSettings` in
  `src/lib/club-settings.functions.ts`, the same read the screen makes. Returns
  `email_reply_to` and `payment_details`, or `503 settings_unreadable` (with a
  `Retry-After`) when they cannot be read, never an answer of "nothing set".
  **There is deliberately no action that writes them.** The bank account says
  where members' money goes and the reply-to where their replies to invoices
  and receipts go, so a leaked or misused token that could change either could
  redirect members to somebody else, and nothing on screen would show it. A
  manager changes them on the screen, signed in, after a confirm. What the
  reply-to does: `docs/emails.md`.
- `get_site_banner` / `save_site_banner` (`"29"`) — the notice across the top
  of every public page, read and written through `loadSiteBanner` and
  `writeClubSetting` in `src/lib/club-settings.functions.ts`, the same calls
  `/manager/site-banner` makes. `get_site_banner` returns `{ banner }`, off when
  nobody has set one, or `503 settings_unreadable` (with a `Retry-After`).
  `save_site_banner` takes any of `enabled`, `message`, `link_label` and
  `link_href` and merges them over what is stored, so `{ "enabled": false }`
  turns it off and keeps the message; the merged banner then has to pass
  `siteBannerSchema`, the screen's own rules (`400 invalid_params` otherwise).
  It refuses with `503` rather than merge over a banner it could not read.
  **Its `link_href` can only be a page on this site** (`400 invalid_params`
  otherwise; a full address to this site counts): an outside address is set
  on the screen, because a club-branded link to another site across every
  page is what a leaked token would want. And while the **stored** link goes
  to another site (one a manager set on the screen), the only change allowed
  is switching the banner off or replacing that link with a page here
  (`409 outside_link` otherwise), so a token cannot reword or re-enable a
  manager's outside link into a message of its own.
  **Unlike `get_club_settings`, this one is writable**, deliberately: the banner
  is public text, moves no money and no replies, and is undone by saving again,
  the same footing as `save_blog_post`. Product rules: `docs/site-banner.md`.
- `resend_email` (`"22"`) — `{ kind, record_id, client_submission_id? }` sends
  one email again through `resendEmail` in `src/lib/email-resend.functions.ts`,
  the function the screens' Resend buttons post to, so the email is rebuilt from
  today's records the same way and refused for the same reasons. `kind` and
  what `record_id` names are in the manifest. Refusals are the error code
  itself: `404 not_found`; `409 paid | unpaid | cancelled | not_approved |
locked | already_verified` (the record has moved on, checked again at the send);
  `409 already_sent` (that `client_submission_id` already sent this email more
  than a minute ago; mint a new one to send it again); `422 paper | no_address
| dependant | free` (nothing can be sent); `429 rate_limited` with a
  `Retry-After` (once a minute per email per record); `503 email_not_sent`
  (retry with the same `client_submission_id`). Without a
  `client_submission_id` every call is a fresh send. What a resend does and why:
  `docs/emails.md`, "Resending".
- **Announcing a plan** (`"26"`): `save_membership_plan` takes `announce: true`
  with an `announcement_id` (a UUID the caller mints) to email every member
  about the plan once it is saved: the screen's "Email all members about this
  plan" box. It saves through `saveMembershipPlanRow`, then announces through
  `announceMembershipPlan` (`src/lib/plan-announcement.server.ts`), the same
  two calls the screen makes, and returns `announcement` (`recipients`,
  `emailed`, `pending`, `announced_at`). The id is **required**, because it is
  what makes a retry safe: the same id finishes the same announcement and
  emails nobody twice, while a new id announces the plan again on purpose.
  Refusals: `400 invalid_params` for `announce` without an id (before anything
  is saved), `409 submission_conflict` for an id already used on another plan,
  and `502 announcement_failed` when the plan saved but the email did not (the
  plan's id is in `error.details`, so the caller retries with that id rather
  than creating the plan again), and `404 not_found` for an `id` that matches
  no plan. `list_membership_plans` reports each plan's `last_announcement`.
  There is no eligibility rule: any plan can be announced, as on the screen.
  Product rules: `docs/notifications.md`, "A plan is announced".
- `delete_invoice` — delete an invoice outright, for tidying up one that should
  never have existed. Dispatches to `deleteMembershipRow`, which the manager
  screens' Delete button also calls, so both refuse for the same reasons in the
  same words. Refused with `409 invoice_not_deletable` when a payment is
  recorded against it, or when a class was checked in against it;
  `error.details.blockers` lists **every** reason at once (`paid | attended`),
  because a caller that fixes one and retries into the next has burned two calls
  to learn what one could have told it. Being **active is not a blocker**: every
  membership is authorised from the moment it is raised, so refusing on it would
  refuse everything. There is
  deliberately **no confirm flag**: unlike `edit_invoice`'s paid guard these are
  not a caller's judgement call, so a paid invoice is never deletable and is
  cancelled instead. The `attended` blocker exists because
  `session_checkins.membership_id` is `ON DELETE SET NULL` — without it the
  delete would succeed and silently turn a class somebody attended into an
  uncovered one. Clearing it means moving those check-ins to another membership,
  which is a **manager-screen action with no agent equivalent**: this API has no
  check-in actions at all, and adding the first one is a wider surface decision
  than the change that introduced this made on its own.
- `file_waiver` — file a scanned paper waiver (migration / bulk filing from
  paper records). Same params as the manager's paper-upload form
  (`paperWaiverUploadSchema`); dispatches to `filePaperWaiver` in
  `src/lib/waiver.functions.ts`, the same function the web form calls, so an
  agent-filed waiver and a manager's own upload are identical. That includes
  the "who is this for" question: `signing_for` defaults to `"self"` and every
  existing caller keeps working unchanged, while `"dependant"` files for
  somebody on another person's account (the participant's `email` is refused,
  `guardian_email` and `guardian_name` are required, and the participant is
  matched within that guardian's household on name and date of birth). See
  `docs/waivers.md`, rule 1. Always lands
  **pending**: it never approves, emails anyone, or marks the email verified
  — approving is a separate, deliberate manager action because it promotes
  the record, unlocks the login of whoever the club writes to about them (their
  guardian's, for a dependant), emails that person to say the account is active
  and assigns the free trial (docs/waivers.md rule 6). `uploaded_by` on the filed row is always
  the token's owner: a waiver is legal evidence, so every filing names the
  manager who vouched for the scan. Filing a waiver the person already
  has for the same `signed_on` is refused with `409 duplicate_waiver` (the
  colliding rows come back in `error.existing`); `confirm_duplicate` files it
  anyway, for the corrected re-scan that is a genuine second document. The
  check lives in `filePaperWaiver`, so the manager's own upload form gets the
  same speed bump.

- `list_kb_sections` / `save_kb_section` / `delete_kb_section` /
  `list_kb_articles` / `get_kb_article` / `save_kb_article` / `list_kb_comments`
  — the knowledge base, the agent's equivalent of `/manager/kb`. Both go through
  `src/lib/kb-admin.ts`, so an agent-published article and a manager's own are
  the same row written the same way. The rules that are not guessable are in
  `docs/knowledge-base.md`; the one that belongs here is **cross-references**:
  an article links to a section of another with an ordinary markdown link
  carrying the heading's anchor (`[the fees](/kb/belts#fees)`), and
  `get_kb_article` reports every anchor the article has in `sections`
  (`id`, `text`, `depth`, `pinned`, `url`). Take the `url` from there rather
  than deriving a fragment from the heading's wording, which is right until
  somebody rewords the heading. Ending a heading with the attribute syntax
  `## How grading works {#grading}` pins its anchor so the rewording does not
  break the link; the suffix is stripped before a reader sees it, and
  `sections[].pinned` says which anchors were set that way.
- `list_waiver_templates` / `get_waiver_template` / `save_waiver_template` /
  `publish_waiver_template` — the waiver everyone signs, the agent's equivalent
  of `/manager/waiver-template`. They go through `listWaiverTemplateRows`,
  `loadWaiverTemplateVersion`, `saveWaiverTemplateVersion` and
  `promoteWaiverTemplate` in `src/lib/waiver.functions.ts` — the same functions
  the editor screen's server functions call, so an agent-published version and a
  manager's own are the same row written the same way. Three things are worth
  knowing before touching them:
  - **They key on the version number, not the row id.** The screen holds the row
    it just listed; an agent reads a list, decides, and calls back later. The
    version is unique on the table and is the number a manager reads off the
    screen and off a signed PDF.
  - **Saving publishes.** There is no draft state (the screen has none either),
    so `save_waiver_template` writes a new version and makes it live in one call.
    Waivers already signed keep the version they were signed against, which is
    what makes this safe to get wrong and then roll back with
    `publish_waiver_template`.
  - **An omitted field is carried over** from the version the edit starts from
    (the live one, unless `base_version` names another), so rewording one
    acknowledgement does not mean resending 30000 characters of legal text and
    risking a body retyped from memory. `title` and `body_md` still travel
    together, and a call naming neither text nor acknowledgements is refused
    rather than republishing an identical copy under a new number. The result's
    `based_on` names the version an omitted field came from.

  Failures are classified rather than flattened, because SKILL.md tells agents a
  4xx means the request has to change: a change that did not reach the live
  waiver (a concurrent promotion, a failed write) is `503
waiver_template_not_published` with a `Retry-After`, and it carries
  `error.details.version` when a version WAS written and is merely unpublished —
  the case where saving again would file a second numbered draft and publishing
  that version finishes the job. `DocumentVersionError` in
  `src/lib/document-versions.ts` carries the reason (`not_found` |
  `invalid` | `not_published`) that decides this; the editor screen shows the
  same message either way.

  Every version must carry the `media` acknowledgement with real wording
  (`hasMediaAcknowledgement`), or the club stops recording who agreed to photos;
  both the save and the publish refuse without it. That check now runs **before**
  the insert rather than only inside `promoteWaiverTemplate`, so a refused save
  no longer leaves an unwanted draft version behind in the editor's list.

- `list_code_of_conduct_versions` / `get_code_of_conduct` /
  `save_code_of_conduct` / `publish_code_of_conduct` — the club's code of
  conduct, the agent's equivalent of `/manager/code-of-conduct`. Both go through
  `listCodeOfConductVersionRows`, `loadCodeOfConductVersion`,
  `saveCodeOfConductVersion` and `promoteCodeOfConductVersion` in
  `src/lib/code-of-conduct.functions.ts`, and promotion through the same
  `promoteDocumentVersion` the waiver uses, so the contract is the waiver
  template's: version-keyed, saving publishes, omitted text carried over from
  `base_version` with `based_on` naming it, and the same classified refusals
  (`503 code_of_conduct_not_published` with `Retry-After` and
  `error.details.version`). Two things are the code of conduct's own:
  - **`asks_reagreement`** (default false) is stored on the version and decides
    who is out of date (`docs/code-of-conduct.md`, rule 3). The save's reply
    carries `reprompted`, the number of people it put out of date, counted on
    every save (a correction made while nothing is live inherits the newest
    version's requirement and can re-prompt people) and before the write, so a
    failed count refuses the call rather than reporting a number nobody
    checked. `publish_code_of_conduct` reports `reprompted` the same way, the
    number the editor's confirm shows before a manager makes a version live. A
    call with no new text is refused unless it asks, which is how a rewrite
    published without asking gets its ask afterwards.
  - **`client_submission_id`** makes a save safe to retry, as on
    `create_item_invoice`: the same id comes back as the version it already
    wrote, with `already_saved: true` and `reprompted: 0`. If that version is
    not live (its first attempt lost the promotion, or somebody published or
    rolled back since), the replay is refused as `503
code_of_conduct_not_published` with its `version`, and nothing is made
    live: promoting it on a retry could silently replace another manager's
    version or undo a deliberate rollback.
  - **`list_code_of_conduct_versions` reads no text.** It reports
    `first_published_at`, which the `Previous` label uses so a version rolled
    away from never reads as `Draft`.
- `list_blog_posts` / `get_blog_post` / `save_blog_post` / `delete_blog_post` /
  `upload_blog_image` (`"25"`) / `start_blog_image_upload` (`"31"`) — the blog, the agent's equivalent of
  `/manager/blog`. Every write goes through the plain functions in
  `src/lib/blog.functions.ts` that the editor's server functions also call
  (`createBlogPostRow`, `updateBlogPostRow`, `deleteBlogPostRow`,
  `storeBlogImage`), so an agent-published post and a manager's own are the same
  row written the same way: slug and excerpt resolution, the publish-date rule
  and the announcement are the editor's. Product rules: `docs/blog.md`. What is
  the agent's alone, and why:
  - **An omitted field keeps its stored value** on a change
    (`mergeAgentBlogPostEdit` in `src/lib/manager-agent.ts`). The editor always
    sends the whole form, so the shared writer reads a missing `status` as draft
    and a missing cover as none; passed straight through, an agent fixing a typo
    would unpublish the post. Publishing a draft is `{id, status: "published"}`.
  - **Publishing is announced**, exactly as on the screen: the first time a post
    goes live, members who opted in hear about it in their daily summary
    (`docs/notifications.md`). The result's `announced` says whether this save
    did it, so the agent can tell the manager.
  - **A create never suffixes a taken address.** The editor turns a second
    "Grading day" into `...-grading-day-2`, which is right for a person and
    wrong for a caller retrying a create it never heard back from: that files
    the post twice and announces it twice (the announcement dedupes on the post
    id, and the second post has a new one). So `save_blog_post` refuses with
    `409 slug_taken`, naming the post that holds the address, and the retry
    learns its post already exists. No `client_submission_id`, because that
    would need a column; the address does the same job here.
  - **An edit is guarded against a save in between.** It writes back the
    fields the caller left out from the row it read, so it only lands if
    `updated_at` still matches (`409 post_changed` otherwise). The editor sends
    what is on screen and is not guarded.
  - **A blank `slug` is refused** rather than re-derived. On the screen a blank
    slug makes a new one from the title, which on a live post moves it to a new
    address and breaks every link already shared.
  - **Two addresses per post.** `url` is the public one and is null for a draft
    (the public route 404s on one); `edit_url` is the manager's screen.
  - **`upload_blog_image` takes base64 `data` or a public https `url`** the
    server downloads. The URL route exists because an assistant over MCP cannot
    type out a photo's bytes. Its type is read off the bytes, never declared. The
    download is https only, to a named public host, with every redirect hop
    checked before it is requested, a 15-second limit and the 8 MB cap enforced
    while reading. All of that is `src/lib/blog-image.ts`. Refusals: `422
image_rejected` (will never work) and `502 image_fetch_failed` (the address
    could not be read just now). Storing an image changes no post; the result's
    `path` goes in `cover_image_path` and its `markdown` in `body_md`.
  - **`start_blog_image_upload` (`"31"`) is the route for a file the caller
    holds but cannot send.** Claude on claude.ai has the manager's photo in its
    code-execution sandbox, but an MCP call is text it types, and neither
    `upload_blog_image` route fits: base64 of a real photo is far too long to
    copy out, and the sandbox has no public address to offer. The action
    returns a one-time link and a ready `curl` command; the sandbox POSTs the
    raw bytes to `/api/manager/blog-image`
    (`src/routes/api/manager/blog-image.ts`) with the link's token as its
    bearer header, and gets back the same `path` / `url` / `markdown`. What
    the token is and is not, all in `src/lib/blog-image-ticket.ts`:
    - **Not a manager credential.** It is a signed ticket (HMAC, key derived
      by HKDF from the service-role key), and storing one image is all it can
      do. That endpoint takes no other credential, and the agent endpoint does
      not take a ticket. The upload re-checks that the manager who asked still
      holds the role. It is not tied to the credential it was asked with, so
      revoking a leaked API token or an assistant's sign-in leaves links
      already minted with it working until their hour is up; removing the
      manager role does void them. Accepted, because tying it would cost a
      lookup per upload to guard an hour of storing pictures that show
      nowhere until a manager publishes them.
    - **Works once, for an hour.** The image is stored under the ticket's own
      id, which the upload looks for first, so a second use is
      `409 already_uploaded` with the first image's `path` / `url` /
      `markdown` in `error.details` (usually a retry whose answer was lost).
      That answer is given even after the hour is up, so a late retry is not
      told to upload again. No table holds tickets: the bucket is the record.
      A rejected or interrupted upload stores nothing, so the same link can be
      used again. The one gap: two uploads racing on one link with files of
      different types both land, because the file's extension is part of its
      name. Only the link's holder can do that, and all it costs is an extra
      unused file.
    - **The link points at `SITE_ORIGIN`**, wherever it was asked from, by
      `linkOrigin`: a ticket only verifies on the server that signed it, and
      the live address is the one host that does not redirect a bearer header
      away. A loopback stack asked over HTTP gets a link to itself. Over MCP
      the SDK does not say which host was asked, so it is the live site, and
      a local stack (its own database on a loopback host) refuses with
      `503 upload_links_unavailable` rather than hand out a link its ticket
      cannot pass.
    - **The command reads the file's path from a shell variable**
      (`--data-binary "@$IMAGE_FILE"`), because a pasted path with an
      apostrophe in it would end a quoted string early.
    - **The sandbox has to be allowed to reach the site.** claude.ai's code
      execution only reaches package registries by default, so the manager adds
      the club's domain to its allowed domains once. Nothing on our side can do
      that for them; the manifest tells the assistant to say so rather than
      fall back to typing base64.

  - **`delete_blog_post` has no confirm flag**, like `delete_invoice`: it is the
    caller's job to ask the manager first. It removes the post's comments with
    it (`ON DELETE CASCADE`), and writes an audit line to the server log.

- `list_contact_messages` / `mark_contact_messages_seen` /
  `delete_contact_message` (`"32"`) — the contact inbox, the agent's equivalent
  of `/manager/contact-messages`. The read is `loadContactMessages`, the
  acknowledgement `acknowledgeContactMessages` and the delete
  `deleteContactMessageRow`, the same calls the screen makes. One difference,
  on purpose, and the guards that follow from it:
  - **Reading marks nothing seen.** The screen stamps the club-wide seen marker
    as soon as it loads; the list action never does. That marker clears every
    manager's "needs attention" item, so an agent reading the inbox for its
    own reasons (a summary, a draft reply) must not clear it for them.
    Acknowledging is `mark_contact_messages_seen`, made when the manager asks.
  - **Its `seen_at` must be a message's arrival time** (`422 not_a_message`
    otherwise), checked by `acknowledgeContactMessages`, which the screen's
    `markContactMessagesSeen` calls too, so both enforce one rule. The screen
    only ever sends the boundary it rendered; an agent could improvise "now",
    which would mark seen whatever arrived after the list was read. The match
    is by instant and to the millisecond (a client re-serialising the timestamp
    keeps no more), and what is stamped is the message's own `created_at` as
    the database renders it: markers are compared as text, so a caller's string
    in another offset would sort wrongly.
  - **What it cannot check is that the caller showed every message before
    `seen_at`.** That half is the caller's, as it is the screen's: `newest_at`
    is null on a truncated list, and the skill tells agents never to substitute
    a row's `created_at` from one. Enforcing it would need the server to know
    what was shown, which it does not.
  - **A marker that cannot be read is refused** on both actions, as
    `503 settings_unreadable` with nothing written. The screen degrades it to
    "everything is unread", which an agent would report as an inbox nobody had
    ever opened (`seenFailed` on `loadContactMessages`), and marking needs the
    current marker for the only-moves-forward guard (`src/lib/seen-markers.ts`).
  - `unread_count` counts the messages returned, not the whole inbox.
  - **The delete has no confirm flag**, like `delete_blog_post`: asking the
    manager is the caller's job, and the skill says so. It is part of the
    club's erasure path (`docs/erasing-personal-data.md`), writes an audit line
    to the server log, and `404 not_found` when the message is already gone.

### `file_waiver`: the parts that have bitten us

- **The address is taken in parts (`address_parts`), and the API also takes
  one line (`address`) where the screen does not.** That is deliberate, not
  drift. Both send parts when they have them and both store the same thing for
  them (`resolveAddressInput` in `src/lib/au-address.ts`). A manager at the
  screen can look up a missing postcode before pressing Sign; an agent working
  through a stack of old records cannot always split what is written, and
  guessing a postcode to make it fit would put a wrong one on a signed
  document. A one-line address is also how an address outside Australia goes, from
  every surface: the screens build it from their "outside Australia" boxes,
  and an agent sends it as `address`. A line is stored as written with no parts, and the person is asked
  for them the next time they give an address. Changing either surface's rule
  means changing this bullet.
- **The two surfaces present that one check differently on purpose, and
  this is not an inconsistency to tidy up.** The HTTP API returns
  `409 duplicate_waiver`, because a machine caller needs a distinct status
  to branch on. `uploadPaperWaiver` instead returns a `filed: false` result
  carrying the collision, so the screen can show the manager _what_ it hit
  and offer "file it anyway". A thrown error would reach the form as a
  toast with the detail lost, which is what makes the guard useless to a
  human.
- The check is **check-then-insert, so it cannot stop two racing retries**
  — neither sees a row the other has not committed. `client_submission_id`
  is what makes a retry safe: same key, same waiver, enforced by the partial
  unique index from `20260729020000`, exactly as the online signing path
  uses it. That index covers the WHOLE table, so the key namespace is shared
  with the public signing path — both lookups therefore ignore anything that
  is not a paper filing, or a caller-chosen id could resolve to a waiver a
  signer's browser minted. Scoping uniqueness per caller
  (`(uploaded_by, client_submission_id)`) would need a migration and is a
  deliberate follow-up, not an oversight.
- Comparing `signed_at` to the string this code WRITES never matches:
  PostgREST renders TIMESTAMPTZ as `+00:00` with no fractional part. Compare
  the date part. This killed the whole idempotency path once, and the test
  fixture hid it by using the write format.
- Sending a key **transfers an obligation**: a failed filing keeps its row
  for the retry instead of deleting it, so an abandoned attempt leaves a
  documentless waiver. `setWaiverApproval` refuses a waiver with no
  `pdf_path` so that row can never become somebody's ACTIVE record, and the
  manifest says the obligation exists.
- A failed probe is `503 duplicate_check_failed` with a `Retry-After`
  header, deliberately distinct from `file_waiver_failed` and deliberately
  silent about `confirm_duplicate` — offering that flag as the fix for an
  outage invites a retry policy to disable the guard wholesale. The 503 is
  documented as "nothing was filed, safe to retry unchanged", which is true
  only because the probe runs BEFORE `resolvePersonId`. Moving person
  creation above it would strand an auth user per retry, and no status-code
  test would notice.
- The probe matches a **UTC-day range**, not the midnight instant a paper
  filing writes, so it catches an online signature on the same day too. The
  club is UTC+10/+11, so a Sydney-morning signature falls on the previous
  UTC day — known and accepted, since widening to the club's own day would
  collide across two dates instead.
- `paperWaiverUploadSchema` is `.strict()`, matching `editInvoiceSchema`. A
  misspelled `confirm_duplicate` would otherwise be stripped by Zod, default
  to false, and return the same 409 forever while the message told the
  caller to do what they thought they just did.

## Agent glue

`.claude/skills/uts-manager-agent/` — a skill (with a `curl` helper) that
documents how to call the endpoint. An MCP wrapper is equally simple: one tool
per manifest action, forwarding to this endpoint.

## Keep these in sync

### The screens and the API report the same thing

A manager screen and this API answer the same questions about the same data,
so they must give the same answer. `get_user` exists because they did not:
the person page and `list_users` were built separately, and the API could not
see a person's code of conduct, verification, profile or waivers while the page
showed all of it. The rule, in both directions:

- **A manager read shown on a manager screen is reported by the API from the
  same function.** Pull the screen's read out of its `createServerFn` handler
  into a plain function taking the client (`loadClubUser`, `kb-admin.ts`), call
  it from both, and project its result. Never write a second query set in
  `manager-agent-actions.ts`. A field the API deliberately does not report is
  listed with its reason (`GET_USER_LEFT_OUT`), not silently dropped.
- **A manager write is either exposed or listed below as screen-only, with the
  reason.** Adding a write to a manager screen means adding it here too, one way
  or the other.

**Screen-only writes, deliberately.** These are on `/manager/users/<id>` and
have no action:

| Write                                               | Why not on the API                                                                                                                                                                                                            |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `setWaiverApproval` (approve a waiver)              | Outward-facing and hard to undo: it emails the person, unlocks the login of whoever the club writes to about them and assigns the free trial (`docs/waivers.md`, rule 6). Needs a product decision before an agent may do it. |
| `setClubUserEmail` (change a login email)           | Moves the person's identity, drops their verified badge and emails the new address. Needs a product decision.                                                                                                                 |
| `setClubUserKitSizes`                               | Reversible and sends nothing, so safe to expose. Not built because no agent workflow has asked for it yet; add it when one does.                                                                                              |
| `getWaiverPdfUrl`                                   | A read, but of a signed legal document with health answers in it, handed out as a bearer link. `has_pdf` says whether there is one. Expose only for a caller that needs the document itself.                                  |
| `attachCheckInCoverage` / `transferCheckInCoverage` | This API has no check-in actions at all, on purpose (see `delete_invoice` above).                                                                                                                                             |
| `setMembershipStatus` to `active` (reopen)          | Recomputes dates and credits; `edit_invoice` refuses `active` for that reason.                                                                                                                                                |

### The four sync points

The action contract lives in **four** places — change all of them together, or
the agent glue drifts from the deployed API:

1. `src/lib/validation.ts` — `managerAgentActions` + the per-action Zod schemas.
2. `src/lib/manager-agent.ts` — `AGENT_MANIFEST` (self-description) + projections.
3. `src/routes/api/manager/agent.ts` — the request dispatch/handlers.
4. `.claude/skills/uts-manager-agent/SKILL.md` — the agent-facing docs.

`src/lib/manager-agent.test.ts` asserts the manifest matches `managerAgentActions`,
so a forgotten manifest update fails CI. The `GET` manifest is authoritative at
runtime: the skill instructs agents to read it before acting, so an MCP/skill
wrapper never needs hand-syncing beyond the human-readable docs above.

**Bump `AGENT_MANIFEST.version` whenever the behaviour a client can rely on
changes**, not only when an action is added or removed. A guard that starts
refusing a call that used to succeed, or a new field in a response, is exactly
what a client needs the version to tell it about. The version is pinned by a
test so the bump is a deliberate edit, and the current value is `"32"`.

**Responses carry `version` too**, not just the manifest, so a client that
cached the manifest at the start of a long run can notice a bump per call
instead of meeting it as an unexplained refusal. Error payload beyond
`code`/`message` is nested under `error.details` — never flat-merged, so the
envelope can grow a reserved key without shadowing a caller's field.

**There is no version pinning.** A caller cannot request the old behaviour; the
contract is latest-only. That is defensible for a single-tenant API with
manager-issued tokens where every caller is known, but it means `changes` is a
record of what already happened, not a negotiation — say so rather than letting
somebody build a client that expects to pin.

**Add a `changes` entry in the same edit**, with `breaking: true` when the
version turns a call that used to succeed into an error. A version number alone says only
that something moved; the client that most needs to know what is the one that
read the manifest at the start of a long import and cannot re-read it mid-run.
A test asserts the head of `changes` matches `version`, so the two cannot drift.
Call out anything that turns a previously-succeeding call into an error — that
is the note a caching client is actually reading for.
