# Item invoices: charging for things that are not a membership

The product spec for charging somebody for a gi, a patch, a grading fee, or
anything else the club sells that is not a membership. `docs/database.md` has the
two tables behind it (`charge_items`, `item_invoices`); keep the three aligned in
the same change.

It is deliberately small, and the smallness is the spec. **No stock, no
categories, no photos, no discounts, no partial payments, no card payments, no
editing an invoice once sent, no refunds, and members cannot buy items
themselves.** If one of those is ever wanted, it is a product decision to raise,
not a field to add.

## The model in one paragraph

A manager keeps a **price list**: each item is a name and a price. They raise an
**item invoice** against a person from that person's page, picking one or more
items with a quantity each. The invoice is emailed straight away with the club's
bank details and its own reference, shows on the member's membership page, and is
settled the way a membership invoice is: a bank transfer quoting the reference,
matched when a statement is imported, or a manager marking it paid. A paid invoice
is finished.

## The price list

On `/manager/items`. Add, rename, reprice, remove. None of these asks first,
because none of them reaches anybody: an invoice keeps **its own copy** of every
line's name and price, taken when it was raised, so changing or removing an item
never changes an invoice already sent. The screen says so beside the price.

Prices are 1 cent to $10,000; names up to 80 characters. The bounds live in
`validation.ts` and again as CHECK constraints, so the agent API cannot store what
the screen would refuse.

## Raising an invoice

From a person's page (`/manager/users/<id>`), **Charge items**. Picking the person
first is how a manager avoids charging the wrong one, which is why there is no
"raise an invoice" on the Items screen.

- **Quantity per line.** The same item cannot appear twice; its quantity goes up
  instead. Up to 20 different items, up to 99 of each.
- **The price comes from the price list at the moment of raising**, never from
  the screen or the request (`buildItemInvoiceLines`). A screen left open while
  somebody repriced an item charges the new price, and an item removed in the
  meantime is refused by name rather than silently dropped.
- **It asks first**, saying who will get the email and for how much, because an
  email cannot be unsent. For a child, it says the guardian gets it.
- **It is safe to retry.** The form goes through `useResilientSubmit`, which
  retries a request that timed out, and a timed-out request may still have
  committed. Each form fill carries a `client_submission_id`; a retry of a raise
  that already landed gets that invoice back and sends nothing (`already_raised`).
- **The email is best-effort.** The invoice is saved first. If the send fails the
  card says so ("raised, but the email did not go out") instead of either
  failing an invoice that exists or claiming an email that never went.

Not a tax invoice: the club is not registered for GST, so nothing says "tax
invoice", ABN or GST, and a test holds that.

## The reference

`INV` plus the invoice number, padded to four digits: `INV0001`, `INV0012`. It is
generated by the database from a sequence, so it is unique by construction and
two invoices for the same person can be outstanding at once. A membership's
reference is per person (`MEMNGUYEN7Q...`), which works for one bill at a time
and would not here. The two shapes never collide.

## Who sees it, and where

- **The member**, on `/membership`: an **Item invoices** card with every invoice
  and its state (paid ones stay, as the record), and anything unpaid also in the
  **How to pay** panel beside membership invoices, with its own reference and a
  copy button. One panel, one way to pay, whatever the bill is for. For a parent,
  the panel covers the whole account, the same as for memberships.
- **The email**, to the person or, for a child, to their guardian, naming the
  child. Subject `Invoice INV0007: $110` (or `Invoice INV0007 for Bea: $110`).
  The bank details block is the same component the membership invoice uses
  (`email-templates/club-account-section.tsx`), so the two can never quote
  different accounts. No manager copy: only a manager can raise one.
- **Managers**, on `/manager/items` (every unpaid invoice, with who owes it) and
  on the person's page (all of theirs).

## Getting paid

- **Bank statement.** Importing a statement on `/manager/reconciliation` settles
  an item invoice when a line carries its reference **as a whole word** and
  **exactly** its total. Whole word because references are sequential: a
  substring match would let a transfer for `INV0012` settle `INV001`. A line that
  fits more than one invoice, or the wrong amount, is left for a manager. The
  membership pass runs first and the item pass only sees what it left, so one
  transfer never pays two things. A leftover line can be matched to an item
  invoice by hand from the same screen.
- **Mark as paid**, for cash at the door. Asks first: it emails a receipt and
  makes the invoice permanent.

Both go through `recordItemInvoicePayment`, the only writer of `paid_at`, which is
guarded on the invoice still being unpaid at the moment of writing: two managers
pressing at once, or a manual mark racing an import, record one payment and send
one receipt.

## Closing one off

| Action | Allowed when        | What happens                                                           |
| ------ | ------------------- | ---------------------------------------------------------------------- |
| Cancel | unpaid              | Kept, marked cancelled, no longer owed. Nothing emailed. No reopening. |
| Delete | unpaid or cancelled | Gone, as though never raised. Nothing emailed. No undo.                |
| (none) | paid                | Finished. The club's record that money moved.                          |

Both confirms say there is no undo, and the delete confirm points out that the
member may already have the email. Both are guarded on the write itself, so a
payment landing mid-click wins.

## Manager screens & the manager agent API

| Manager UI                             | Agent actions                                                            |
| -------------------------------------- | ------------------------------------------------------------------------ |
| `/manager/items` price list            | `list_items` / `save_item` / `delete_item`                               |
| `/manager/users/<id>` Charge items     | `create_item_invoice`                                                    |
| `/manager/items`, person's page        | `list_item_invoices`                                                     |
| row actions on both                    | `mark_item_invoice_paid` / `cancel_item_invoice` / `delete_item_invoice` |
| `/manager/reconciliation` manual match | none (the API has no bank-statement actions)                             |

Both call the same shared functions in `src/lib/item-invoices.functions.ts`. The
pure rules (state, totals, the statement match) are in `src/lib/item-invoices.ts`.
